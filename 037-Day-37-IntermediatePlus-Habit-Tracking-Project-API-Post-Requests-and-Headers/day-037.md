# Day 37 — API POST/PUT/DELETE & Headers — Pixela Habit Tracker

## Core Concepts
- **HTTP verbs as operations** — POST creates, PUT updates, DELETE removes; each maps to its own endpoint.
- **Header authentication** — `X-USER-TOKEN` keeps the secret out of the URL; keys in query params leak into server/proxy logs.
- **Environment variable namespacing** — `load_dotenv()` does not override existing variables; `USERNAME` collides with the Linux system variable. Prefix project vars: `PIXELA_USERNAME`, `PIXELA_TOKEN`.
- **`requests` exception hierarchy** — `RequestException` is the base; catch the broadest exception that can actually be handled, let the rest propagate.
- **Pixela response contract** — failures may return HTTP 200 with `"isSuccess": false`; verify both status and body.

## Syntax / Key Commands
```python
HEADERS = {"X-USER-TOKEN": os.getenv("PIXELA_TOKEN")}
response = requests.post(url=endpoint, json=params, headers=HEADERS)
response.raise_for_status()
```
```python
try:
    response = requests.post(...)
    response.raise_for_status()
except requests.exceptions.RequestException as e:
    print(f"Request failed: {e}")
```
```python
load_dotenv()   # namespaced vars only; never reuse USERNAME, HOME, PATH, SHELL
```

## Pitfalls
| Mistake | Why It Happens | Fix |
|---------|----------------|-----|
| `os.getenv("USERNAME")` returns system user | `USERNAME` exists as a system variable; `load_dotenv()` won't override | Namespace project vars (`PIXELA_USERNAME`); or `load_dotenv(override=True)` |
| Trusting `raise_for_status()` alone | Pixela can fail with HTTP 200 + `"isSuccess": false` | Check the JSON body: `data.get("isSuccess")` |
| Treating 404 as an error on pixel lookup | Pixel for a date may not exist yet | Map 404 → quantity 0; raise on other statuses |
| Secrets in query params | Convenience | Send tokens via request headers |
